# ADR 0082: Fix a reproducible Racc performance comparison contract

- Status: Accepted
- Date: 2026-07-27

## Context

The versioned pipeline benchmark in ADR 0038 measures Ibex consistently, but
it does not define a two-implementation experiment. The external measurements
used by ADR 0081 recorded their outcomes in release-readiness documentation
without retaining executable scenario definitions. Parser construction,
process startup, lexing, parser instance allocation, YJIT, and Racc's runtime
backend can each change the apparent gap.

A performance target is not actionable until repeated measurements preserve
those distinctions. The experiment must also remain within the stable table,
semantic-action, runtime-hook, and event contracts fixed by ADRs 0002 and
0050.

The repository-owned representative grammar returns `false` at end of input,
which Ibex accepts but Racc's native runtime does not. Changing that committed
grammar would invalidate the current benchmark source digest and blur its
append-only history. Measuring only a wrapper around `next_token` would add a
method call to every token and disproportionately distort the faster runtime.

## Decision

`benchmark/comparison.rb` is the version-1, repository-owned comparison
protocol. Its JSON output is validated by
`schema/performance-comparison-v1.schema.json`.

Every formal report uses at least ten fresh worker processes for each
implementation and scenario. Ibex-first and Racc-first execution alternate by
run to limit ordering drift. The protocol records exact command templates,
revision and dirty state, Ruby and Racc versions, OS, CPU, processor count,
Ruby executable, YJIT availability and state, workload digests, iteration
policy, and the observable Racc runtime backend. YJIT-off and YJIT-on reports
are distinct environments and are never pooled.

Dirty state includes tracked and untracked paths as separate booleans. Kernel
release and a best-effort CPU model distinguish hosts that share a generic
architecture label. `RUBYOPT` is never copied verbatim: the report records
whether it is present, its byte count and SHA-256 identity, plus option names
with values and paths redacted. Every worker reports its effective YJIT state
and `RUBYOPT` identity; report assembly rejects a worker that differs from the
parent environment.

Cold generation measures a fresh CLI subprocess and generated byte size.
Warm runtime workers generate and load a parser outside the measured region,
perform the configured warmup, and then record elapsed time and
`GC.stat(:total_allocated_objects)` deltas per parse. Runtime is split across
two independent dimensions:

- lexer-inclusive input and a pretokenized input stream; and
- parser instance reuse and a new parser instance for every parse.

After the timed and allocation-counted region, every worker performs a
separately bounded repeated-result probe. A sequence digest covers every probe
result rather than only the last parse. The sequence length and digest must
agree across all four runtime scenarios and both implementations.

The worker derives a temporary comparison grammar from the checked-in
representative grammar. It changes only the EOF return to `[false, false]` and
adds a pretokenized driver implemented in the grammar's own user-code section.
Both generators receive the same derived bytes. The report records the
checked-in and derived grammar SHA-256 digests plus the named adaptation.
Historical benchmark inputs and artifacts are not rewritten. Generated Racc
source remains a black-box artifact: the harness invokes the public CLI, loads
the result, and observes behavior without reading or transforming generated
Racc code.

Result and behavior SHA-256 digests must be identical across implementations,
drivers, and parser lifecycles before a report is emitted. Generated byte size
must be stable within an implementation and scenario. Runtime backend is
classified as `native` only when the running process exposes a loaded
`cparse` extension feature; otherwise it is `ruby`.

The expected Racc backend is an explicit report setting and defaults to
`native`. Mixed backend observations or any backend other than the configured
one reject the report before comparison statistics are emitted. This prevents
an apparently passing target from being attributed to a different Racc
runtime. A diagnostic Ruby-backend run must opt in explicitly and remains a
separate configuration.

Each time or allocation series reports its median, median absolute deviation,
minimum, and maximum. A deterministic independent bootstrap reports the 95%
interval for the Ibex-to-Racc median ratio. `target_met` is true only when the
interval's upper bound is at most `1.0`. It is evidence in the artifact, not a
CI timing threshold. Structural tests validate the protocol and schema; noisy
wall-clock outcomes do not fail ordinary CI.

The workload seed is non-negative and the behavior probe is capped at 100
parses per worker. The completely assembled document is validated against the
checked-in schema before it is written or printed.

This owned workload is the control experiment, not a substitute for the three
public-gem workloads required by ADR 0081. Those adapters must use the same
environment, isolation, scenario, digest, and statistical contract before
their results can change the v1 hold decision.

## Consequences

- Performance changes can be evaluated one at a time against a repeatable
  control instead of incomparable one-off timings.
- Lexer cost and parser construction cost can no longer be silently moved
  into or out of a runtime claim.
- Racc's native and Ruby backends, YJIT state, and parser lifecycle remain
  visible in every artifact.
- The stable parser-table, semantic-action, hook, and event contracts are not
  weakened to obtain a faster benchmark result.
- Public-gem adapters and reviewed environment-matched artifacts remain
  required before the performance release gate can pass.
