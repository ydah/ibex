# E002 syntax-only repair result

## Problem evidence

The semantic runtime can replay a selected `RepairPlan`, but editor callers
need byte edits and a fresh syntax result without receiving or inventing an
application semantic value. `RepairPlan#position` is a buffered token index,
not a source range, and the legacy search projection also collapses exhaustion
and no-plan into `nil`.

## Contract

Add a syntax-session repair operation backed by the existing `RepairSearch`.
The operation runs on a fresh syntax-only parser, captures selected token edits
with absolute byte ranges, resolves inserted/replacement spelling from an
explicit string map or a conservative punctuation literal, and validates the
result by applying all edits to `SourceText` and opening a fresh syntax
session. It does not mutate the originating session.

The result contains bounded status, the repair plan, token edit metadata, byte
text edits, the error/missing-token CST, immutable diagnostics, the edited
source, and the fresh validation result. It has no semantic value field. A
successful validation must consume the complete edited source; an error
validation exposes the exact edited source separately and its CST is required
to be a consumed prefix, matching the existing early-accept/error CST
contract.

## Trust label

Production actions are suppressed by the existing syntax-only runtime mode.
Generated lexer actions and other parser hooks remain trusted application code
under the syntax-session execution profile. The operation replaces
`on_repair` on its fresh private parser only to capture data; it does not call
the application's repair callback.

## Compatibility

`RepairSearch#search` retains its current `RepairPlan | NEED_INPUT | nil`
projection for semantic parsers. A typed internal outcome is additive. The
syntax-session operation is additive and Experimental. Existing semantic
repair, fallback recovery, and feature-off parsing remain unchanged.

## Configuration admission

No grammar or CLI configuration is admitted. The caller supplies an immutable
`RepairPolicy` and an optional token-name-to-source-text map. That map supplies
syntax bytes only and never supplies semantic values.

## ABI assessment

The installed runtime and generated parser RBS surfaces gain additive
Experimental classes and one `SyntaxSession` method. Parser table format v6,
Grammar/Automaton IR, manifest, JSON schemas, and grammar syntax do not change.
Embedded generated bytes change and must be regenerated to acquire the API;
old embedded parsers keep their previous behavior.

## Bounds

Repair search retains cost, configuration, lookahead, proof-shift, and stack
bounds. Text edits also obey the session edit-count, inserted-byte, and source
size bounds. Cancellation is checked before search, at runtime events, before
fresh validation, and after validation. Multiple selected repair segments are
reported as unavailable in v1 rather than flattened across changing token
coordinates.

## Oracle

The independent oracle is an apply-and-fresh-syntax-parse. Acceptance requires
no fresh diagnostics and complete source consumption. Progress requires fewer
diagnostics or a strictly later first diagnostic byte. Otherwise the result is
rejected. The repair CST and an error validation CST must be consumed prefixes
of their respective source bytes; the exact edited bytes remain in
`updated_source`.

## Tests

- insertion, deletion, and replacement metadata and byte edits;
- no semantic value and no production action execution;
- apply-and-fresh acceptance/progress/rejection;
- selected/not-found/exhausted bounded outcomes;
- missing token spelling fails closed;
- original session remains unchanged;
- cancellation and service/resource bounds;
- CST source fidelity and immutable result values;
- embedded and installed runtime/RBS loading.

## Claims

The operation proposes and validates syntax edits. It does not claim user
intent, semantic correctness, action purity, diagnostic usefulness, or a
general token spelling synthesis algorithm.

## Kill conditions encountered

No second search engine is introduced. Missing token spelling, overlapping
edits, multiple repair segments, exhaustion, cancellation, and hard resource
limits cannot become successful results. Insertions never receive an
application semantic value.
