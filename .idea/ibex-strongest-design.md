## 1. 戦略: 「最強」を defensible な主張に置き換える

### 1.1 前提条件の直視

敵対的検証の第一の結論は、**第 1 版が前提条件を無視していた**ことだった。

| 前提 | 帰結 |
|---|---|
| v0.1.0、リリース 1 本［確］ | 公開 API の実地検証がまだ薄い |
| Preview に大量の機能がある［確］ | 昇格作業そのものが v1.0 の主要工数 |
| 昇格には「2 リリース仕様変更なし」が必要［確］ | **Preview を 1 つ足すたびに v1.0 が最短 2 マイナー遠のく** |
| 実質 1 メンテナ体制［推］ | 並行して進められるのは 1〜2 本 |
| ランタイム依存 0、Pure Ruby［確］ | 性能で C 実装系に正面から勝つのは構造的に困難 |

したがって「全方位で世界最強」は戦略として成立しない。tree-sitter（インクリメンタル）、ANTLR（エコシステム規模）、bison（普及度）と全領域で戦えば、どこにも勝てないまま v1.0 に到達しない。

### 1.2 勝てる主張（moat）と戦わない領域

ibex の実際の差別化要因は**契約の厳格さと診断の質**である［確: 段階境界、IR 凍結、非実行解析、文表キーのメッセージカタログ、反例と到達性証人の区別］。ここを深掘りするのが唯一の勝ち筋。

**主張する領域（moat）**

1. **LR 系で世界最高の診断**: 競合を説明するだけでなく、**直し方を提示し、直した結果が言語を変えていないことを検査できる**。（`explain` + `fix` + `equiv`）
2. **大規模文法を安全に保守できる**: 表の独立検証、有界同値検査、差分レポート、機械検査される不変条件。「`parse.y` 級の文法を怖がらずに触れる」状態を作る。
3. **契約の透明性**: バージョン付き IR、バイト安定、非実行解析、成熟度の明示。研究・教育・長期保守で選ばれる理由になる。

**戦わない領域（明示的に負けを認める）**

| 領域 | 勝者 | ibex の立場 |
|---|---|---|
| 生パース速度（C 実装比） | bison / re2c | Pure Ruby の範囲で実用。C ターゲットは需要とスポンサーが確認できた場合だけ検討 |
| エディタ用インクリメンタルの成熟度 | tree-sitter | 追いつく目標は置かない。既存 Experimental を正しく Stable にするだけ |
| 対応言語・文法の在庫 | ANTLR | 自作ギャラリーで十分。他人の文法を取り込むのは検証用途に限る |
| ランタイムの言語数 | ANTLR | Ruby を主、他は「同一挙動を証明できる範囲で」任意 |

この表を README に書けるようにするのが第 2 版の目標である。**「最強」を「特定軸で反論不能」に置き換える。**

### 1.3 勝利条件（測定してから宣言する方式）

第 1 版は未測定の数値を目標として書いた。これは達成不能な約束になる危険がある。第 2 版では**「まず測る → 基準を文書化する → 次の基準を宣言する」**の順にする（既存の SP-4 修復評価が 8/10 という実測を根拠にしている作法［確］に合わせる）。

| # | 勝利条件 | v1.0 での要件 | 数値目標 |
|---|---|---|---|
| W1 | 表の正しさが独立に検証されている | 全既存アルゴリズム × 全ギャラリー文法で `ibex verify` 合格。故意に注入した欠陥を検出できることを実証 | 注入欠陥 20 件の検出率 100% |
| W2 | 文法変更の安全性が検査できる | `ibex equiv` が既知の等価／非等価な文法対で正答し、非等価には反例を提示 | 等価 10 組・非等価 10 組で正答 |
| W3 | 競合の直し方を提示できる | `ibex fix` が提案を出し、**提案が言語同値であることを必ず検査済み** | 成功率は**測定して記録**。目標値は第 2 回測定時に宣言 |
| W4 | 退行を機械的に検出できる | 不変条件マトリクス、機能 off のバイト固定、再現ビルド、差分ファジングが CI 必須 | 必須ジョブ 100% 緑 |
| W5 | 性能の基準が公開されている | ベンチ条件（比較対象のランタイム構成を含む）を明記した上で数値を公開 | **比較条件を明記した実測値の公開そのものが要件**。相対目標は測定後に宣言 |
| W6 | Preview が整理されている | 全 Preview 機能に昇格判定の結論（昇格 / 据え置き / 降格 / 削除）がある | 判定率 100% |
| W7 | 互換性を壊していない | Stable API の破壊的変更 0 | 0 件 |

**W5 に関する重要な訂正**: 第 1 版は「pure Ruby で racc 比 1.0x 以上」と書いたが、これは比較条件を明示しない不正な目標である。racc には C 拡張ランタイムを使う構成があり［推］、Pure Ruby の ibex と同一条件ではない。ベンチマークは必ず

- 比較対象の**ランタイム構成**（拡張の有無）
- Ruby バージョンと YJIT の有無
- 入力コーパスと測定回数

を記録し、条件を書かずに「◯◯比」と主張してはならない。既存の「タイミングと RSS は非ゲート、CI は決定的な構造とダイジェストのみ再現」という方針［確］は維持する。ゲート化するのは**相対退行（前リリース比）**のみとする。

### 1.4 非目標（第 1 版から変更なし＋追加）

1. 汎用パーサコンビネータ／任意バックトラック PEG の実行モデル
2. 意味解析基盤（型検査器・名前解決）
3. **実行時に任意コードを評価する意味述語を Stable にすること**
4. 正規表現エンジンの完全独自実装
5. **（追加）全方位の性能競争**。§1.2 の「戦わない領域」を非目標として明文化する
6. **（追加）他プロジェクトの文法資産の同梱**。ライセンス汚染を避けるため、ギャラリーは自作文法のみ（§5.7）

## 2. 最大の制約: 拡張速度を機能予算で制御する

### 2.1 Preview 債務の計算

昇格条件は「代表的な文法での実使用、機能固有の不変条件／性質試験、**仕様変更なしの 2 リリース**、依存ツールの対応、完全な公開文書」［確］。ここから機械的に次が導ける。

```
v1.0 到達時期 ≧ 最後に仕様が変わった Preview 機能の時刻 + 2 マイナーリリース
```

現在 Preview にある機能群［確］は、EBNF・パラメータ化規則・インライン規則・中間アクション・複数エントリ・import・生成レキサ・意味位置／型・AST 生成・文法テスト・文書ツール・IELR・LSP・watch・debug・coverage・playground・action-shadow と広い。**この集合に 1 つ足すたびに、v1.0 の下限が後退する。**

第 1 版は約 40 の新 Preview 機能を提案していた。これは v1.0 を事実上無期限に遠ざける提案であり、**設計として有害**だった。

**現行ポリシー**: feature 開発は凍結しない。第三者レビュー待ちの v1.0 `HOLD` はリリース判定として維持するが、開発可否をその判定に連動させない。上記の Preview 債務リスクは消えていないため、以下の同時実行予算で制御する。公開済みの Grammar IR / Automaton IR の契約凍結は別の互換性規則として維持する。

### 2.2 機能予算（Feature Budget）

そこで次を設計上の硬い制約とする。

> **B1. v1.0 のリリース判定と feature 開発の可否を分離する。**
> リリースが `HOLD` でも、互換性・成熟度・品質ゲートを満たす feature 開発は進めてよい。`HOLD` 中の変更を v1.0 に含めるかは、正確なリリース候補 revision で全ゲートを再実行して別途判断する。
>
> **B2. 新規 Preview 開発トラックは同時に 3 個までとする。**
> 4 個目を始める前に、どれか 1 つを Stable、Experimental、または削除に落とす。既存 Preview のうち仕様変更を伴わない昇格作業はこの枠を消費しない。
>
> **B3. 新規の文法構文（`%`宣言・`@`注釈）を含む開発トラックは同時に 1 個までとする。**
> 構文の EBNF、意味、互換モードでの拒否、IR の版、撤退条件を ADR で確定してから利用者向け変更をマージする。
>
> **B4. Experimental の同時数は 5 個まで。** 超えたら古いものを削除する（Experimental は予告なく変更・削除可能［確］）。

「開発トラック」は最初の利用者向け変更をマージした時点から、Stable / Experimental / 削除の判定までを指す。S0 調査、S1 ADR、マージしない S2 スパイクは予算を消費しない。既存 Preview の仕様変更を再開する場合は新規トラックとして数える。

この予算があると、以降の提案カタログ（§6）は「やることリスト」ではなく**「選択肢の在庫」**として読める。これが第 1 版との最大の違いである。

### 2.3 提案の 3 層分類

| 層 | 定義 | 個数 | 節 |
|---|---|---|---|
| **T0** | 既存機能の安全性と昇格を支える基盤。新しい文法構文を追加せず、生成物を変えない | 9 | §5 |
| **T1** | B2〜B4 の予算内で取り出せる選択肢の在庫。v1.0 の公開時期とは切り離す | 44 | §6 |
| **T2** | 却下または長期保留。理由を記録する | 11 | §12 |

T0 に入る条件（**すべて**満たすこと）:

1. 新しい文法構文を追加しない
2. 生成されるパーサの挙動を変えない（＝生成物がバイト同一）
3. 既存機能の**昇格を助ける**か、**退行検出を強化する**
4. 単体で価値が出る（他の T0 の完成を待たない）

## 4. アーキテクチャへの変更は最小に留める

### 4.1 第 1 版の設計変更を撤回する

第 1 版は Semantics IR / TokenFilter IR / Target IR の 3 つの新段を提案した。敵対的検証の結論: **feature 開発を凍結しない現行ポリシーでも、需要のない段を先回りして入れると Grammar IR v3 の設計を早すぎる時点で固定するリスク（R02）が大きい。** これらは B2〜B4 の予算に空きがあるだけでは着手せず、実在するユースケースと撤退条件を ADR に記録できた場合に限る。

第 2 版では次のようにする。

| 新段 | 第 1 版 | 第 2 版 |
|---|---|---|
| TokenFilter IR | P13 で導入 | **T1 に降格**。導入時は Lexer IR の次版に埋め込む（独立 IR を増やさない） |
| Semantics IR | P16 で導入 | **T1 に降格**。`@fmt` 等が実際に必要になった時点で判断 |
| Target IR | P18 で導入 | **T1 に降格**。ただし「Ruby 生成器を Target IR 経由に書き換えても生成物がバイト同一」という検査は先に用意できる |
| Grammar IR v3 | P15 で封筒を切る | 実機能が必要とする時点まで作らない。空の封筒だけを先行追加しない |

### 4.2 T0 が触る範囲（＝v1.0 までのアーキテクチャ変更）

**T0 は既存の段境界を 1 つも変えない。** 追加されるのは Grammar IR / Automaton IR を**読むだけ**の解析ツール群である。

```
                     既存パイプライン（変更なし）
 .y / DSL → Frontend → Normalizer → Grammar IR v2 → Builder → Automaton IR v2 → 生成器
                                        │                          │
                                        │                          │  ← 読むだけ
                        ┌───────────────┴──────────────────────────┴────────────┐
                        │                    T0 で追加する層                      │
                        │  verify（表の独立検証）                                 │
                        │  equiv（2 文法の有界同値検査）                          │
                        │  fix（競合修復候補の生成と検証）                        │
                        │  fuzz（文生成と差分試験）                               │
                        │  diff / metrics / reduce                               │
                        │  import bison（外部 → Grammar AST）                     │
                        └────────────────────────────────────────────────────────┘
```

この形の利点:

1. **HR3（機能 off でゼロコスト）が自動的に満たされる。** 生成器に手を入れないので、生成物は 1 バイトも変わらない。
2. **リバートが容易。** 新規ディレクトリの削除で戻せる。
3. **Preview 債務が増えない。** ツールは新しい文法構文や生成時挙動を追加せず、新規 Preview 開発トラックを消費しない。

### 4.3 T1 でアーキテクチャを変える際の順序（拘束条件）

T1 に進む際も、次の順序を守る。

```
① Automaton IR v3 の封筒（フィールド追加なし）
   ↓
② Grammar IR v3 の封筒（フィールド追加なし）
   ↓
③ テーブルフォーマット v7 を「一度に」設計する（R13 対策）
   ↓
④ 個別機能のフィールドを ADR ごとに加算する
```

**③ が重要**。第 1 版は v7 を P14 に置いたが、P14〜P18 の機能が順次 v7 にフィールドを足す構成になっていた。これは v7 の意味が段階的に変わることを意味し、「読み込み継続」の保証が複雑化する。**v7 に入る全フィールドを 1 つの ADR で設計してから実装を始める。**入らないものは v8 にする。

### 5.1 T0-1: 不変条件マトリクスとゼロコスト検査

**目的**: 以降のすべての変更が「壊したかどうか」を機械的に判定できる状態を作る。

**不変条件（既存機能に対して常に成立すべきもの）**

| ID | 不変条件 |
|---|---|
| INV1 | 同一文法から作った全アルゴリズム × 全表形式のパーサが、同一入力に対して同一の受理／拒否を返す |
| INV2 | `@node` 文法では同一の AST を返す |
| INV3 | エラー ID・エラー位置・`expected_tokens` が一致する（アルゴリズム間で仕様上一致すべき範囲で） |
| INV4 | IR の dump → load → dump がバイト同一 |
| INV5 | 同一入力・同一オプションで生成物がバイト同一（環境変数・ロケール・TZ に依存しない） |
| INV6 | リソース制限を超える入力は必ず `ResourceLimitError` で停止する（ハング・OOM しない） |

**組み合わせ**: `test/matrix.yml` に宣言する。

```yaml
axes:
  algorithm: [slr, lalr, ielr, lr1]
  table:     [plain, compact]
  cst:       [off, on]
  locations: [off, on]
  entries:   [single, multi, isolated]
representative: 12   # PR CI
full: true           # nightly（全直積）
```

**ゼロコスト検査の正しい定義（第 1 版の訂正）**

第 1 版は「機能 off の生成物が変更前とバイト同一」を恒久的な条件として書いた。これは誤り: 生成器の正当なリファクタでもバイトは変わるので、恒久固定は不可能である。正しい定義は次のとおり。

> **HR3（訂正版）**: 機能を追加する PR について、**その PR の前後で**、当該機能を使わない代表文法群の生成物がバイト同一であること。生成器のリファクタなど意図的にバイトが変わる PR は、`rake golden:update` で golden を更新し、**差分そのものを PR のレビュー対象にする**。

つまり検査するのは「不変であること」ではなく「**変化が意図的で、レビューされたこと**」である。

**DoD**
- `rake test:matrix`（代表 12 組）と `rake test:matrix:full`（全直積）が動く
- 失敗時に「どの組み合わせのどの不変条件が破れたか」が出る
- `rake test:zero_cost` と `rake golden:update` が動き、golden 差分が PR に現れる
- `rake test:reproducible`（2 回生成のバイト一致、ロケール／TZ 変更下でも）

### 5.2 T0-2: `ibex verify`（表の独立検証）

**位置づけの訂正**: 第 1 版は「新規機能」としたが、実際には**既存の参照ストラテジによるバイト等価証明と固定シード性質試験を、全アルゴリズム・全表形式に一般化するもの**［確］。この位置づけを ADR に明記する。

**検証項目**

| # | 性質 | 実装方針 | 既定 |
|---|---|---|---|
| V1 | 健全性: reduce/shift が正当なアイテム集合に対応する | 状態のアイテム集合を独立に再計算して照合 | ✅ |
| V2 | 完全性: アイテム集合が閉包・後続の定義を満たす | 同上（高コスト） | nightly |
| V3 | 先読み妥当性 | FOLLOW（SLR）／伝播（LALR）／正準（LR1）の定義を独立に再計算 | ✅ |
| V4 | 既定縮約の互換性 | 既定行動を展開しエラーマスク適用後に全セル一致 | ✅ |
| V5 | 表変換の健全性（双模倣） | 変換前後で同一入力列に対する行動列が一致 | nightly |
| V6 | 到達性・生産性 | 全状態が到達可能、全非終端が終端文を導出可能 | ✅ |
| V7 | 停止性 | ε 循環による無限 reduce がない | ✅ |
| V8 | 決定性 | 各セルの行動が一意（**宣言済み resolver を除く**） | ✅ |

**V8 の定式化に関する訂正**: 第 1 版は V8 を「各セルの行動が一意」とし、同時に `%guard` で「解析経路は両分岐可能とみなす」と書いていた。これは矛盾する。正しくは:

> V8: 各 ACTION セルは、(a) 単一の行動を持つ、または (b) 単一の**宣言済み resolver**（優先順位解決・先読み DFA・ガード・`%dprec`）に紐づく複数行動を持つ。resolver を持たない多重行動は違反。

**検証器自体の検証（これが本項目の核）**

検証器が「何も検証していない」状態は容易に起こる。したがって:

- **欠陥注入テスト**: Automaton IR を機械的に壊す 20 種の変異（reduce の生成規則を差し替える、先読みを 1 要素削る、goto を別状態に向ける、既定行動を追加する、到達不能状態を挿入する等）を用意し、**すべてが検出されること**を CI で検査する。
- 検証器は**ビルダのコードを参照せずに実装する**。意図的な重複実装であることを ADR に明記する（既存の参照ストラテジと同じ思想）。

**DoD**
- 既存 4 アルゴリズム × 全ギャラリー文法 × `plain`/`compact` で合格
- 欠陥注入 20 件の検出率 100%
- 終了コード規約（0 成功 / 1 違反検出 / 2 予算切れ / その他 呼び出しエラー）
- ユーザコードを実行しない

### 5.3 T0-3: 文生成器と `ibex fuzz`

**訂正**: 「ファジングがない」のではなく、**固定シードの性質試験はある**［確］。不足は「文法から文を生成して差分を取る」層である。

**構成**

1. **文生成器**（`Ibex::Generate`）: Grammar IR から導出木を生成する。
   - 一様ランダム（深さ・幅の境界付き）／k-path 網羅指向（k=1,2）／シード固定
   - **既存の反例探索の設定探索を再利用する**（新規に探索器を書かない）
   - HR10（予算あり・超過で明示的失敗）、HR11（明示的ワークリスト、Ruby スタック非依存）
2. **検査項目**
   - 生成文は必ず自分の文法で受理される（自己整合性。破れたら生成器かビルダのバグ）
   - 1 トークン変異（挿入・削除・置換）後も**必ず終了する**（クラッシュ・ハング・未捕捉例外なし）
   - アルゴリズム間の差分（INV1〜INV3）
   - 外部との差分（`--against`）。比較条件を必ず記録する
3. **カバレッジ誘導**: 既存の `ibex coverage`（状態・生成規則の被覆）［確］をフィードバックに使い、未到達状態を狙う。
4. **失敗の最小化**: `ibex reduce`（T0-6）で最小化し `test/fuzz/regressions/` に固定シードで保存。

**DoD の訂正**: 第 1 版は「既知バグを 1 件以上検出した実績」を DoD にしていた。**バグの存在を保証できないので DoD にできない**。正しい DoD は検出能力の検証:

- **注入した欠陥を検出できること**: ビルダ・ランタイムに 10 種の欠陥を注入したビルドを用意し、ファジングがすべて検出することを確認する。
- nightly で全ギャラリー文法 × 10^5 文が回る
- 終了コード規約に従う

### 5.4 T0-4: `ibex equiv`（有界言語・木同値検査）

**目的**: 「文法をリファクタしたが言語は変わっていない」を検査する。`ibex fix` の前提であり、moat の中心。

**手法（3 つを併用し、それぞれの限界を明示する）**

| 手法 | できること | できないこと |
|---|---|---|
| E1: 双方向サンプリング | A の生成文を B で、B の生成文を A で検査 | 網羅性がない（見つからない ≠ 等価） |
| E2: 積オートマトンの境界付き探索 | 「A で受理・B で拒否」に到達する**最短の反例**を提示 | 深さ N を超える差異は見つからない |
| E3: 構造的比較 | 正規化後の Grammar IR が同型なら即「等価」と結論できる | 同型でない場合は何も言えない |

**出力の意味を厳密に分ける**（既存の `check --ambiguity` の作法［確］に合わせる）

| 終了コード | 意味 |
|---|---|
| 0 | 宣言した境界内で差異が見つからなかった。**等価の証明ではない** |
| 1 | 差異を発見。反例トークン列を提示（A が受理・B が拒否、またはその逆） |
| 2 | 予算切れ。探索が完了しなかった |

**木同値**: `--map old_rule=new_rule` で対応表を与えたときのみ AST 同型性を検査する。対応表なしでは言語同値のみ。**「木が同じ」を暗黙に仮定しない**。

**DoD**
- 既知の等価 10 組で 0 を返す
- 既知の非等価 10 組で 1 と**具体的な反例**を返す
- 出力に「これは有界検証であり証明ではない」旨と実際に検証した境界値を含む
- 予算切れが 2 で区別される

### 5.5 T0-5: `ibex fix`（競合修復提案）

**これが moat の主戦力**。「競合を説明する」ツールは他にもあるが、「直し方を出して、直した結果が言語を変えていないことを検査する」ツールは存在しない。

**アルゴリズム**

1. 対象競合を選ぶ。既存の反例／到達性証人を取得する［確］。
2. **修復候補を有限空間から列挙する**:
   | 種別 | 候補 |
   |---|---|
   | 宣言の追加 | 競合関与終端への `left`/`right`/`nonassoc`/`%precedence` |
   | 優先順位上書き | 対象生成規則への `= TOKEN` |
   | アルゴリズム変更 | `ielr` / `lr1` に切り替えると消えるか（既存の IELR 助言［確］の一般化） |
   | 構文の機械的変換 | 左再帰↔右再帰、共通接頭辞の因数分解、`%inline` 化／規則の切り出し |
   | 期待値の宣言 | `%expect` / `%expect-rr` の調整（＝「これは意図的な競合である」という提案） |
   | 回復品質 | `%on_error_reduce` / `%recover sync:` の追加（競合を消さないが診断を改善する提案） |
3. 各候補を適用して構築し直し、**次の 3 条件をすべて満たすものだけを提案する**:
   - (a) 対象競合が消える
   - (b) 他の競合が増えない
   - (c) `ibex equiv` で元文法と**有界同値である**
4. 提案には必ず添える: unified diff / 消える競合の ID / **同値検査の境界値** / 副作用（状態数の変化、メッセージカタログへの影響）。
5. 探索は境界付き（候補数・構築回数の上限、超過で終了コード 2）。

**安全装置**

- **(c) を満たさない候補は提示しない。** 「たぶん大丈夫」を出力しない。
- `--apply` は既存 `fmt` と同じトランザクショナル書き込みを使う［確］。適用後に必ず「同値検査は N トークンまでの有界検証であり証明ではない」旨を出力する。
- **メッセージカタログへの影響を必ず報告する**（§7.1）。表が変わればカタログの `moved`/`uncovered` が発生する。

**DoD**
- 代表競合 20 件（ギャラリー + 合成）に対する成功率を**測定して記録する**（目標値は第 1 回測定後に宣言。第 1 版の「60%」は根拠のない数値だったので撤回）
- (c) の検査を通らない提案が 1 件も出ないことを試験
- LSP の code action としても公開できる形にする（T1）

### 5.6 T0-6: `ibex diff` / `metrics` / `reduce`

3 つまとめて 1 項目にする（第 1 版は別項目にして数を膨らませていた）。

| コマンド | 内容 | DoD |
|---|---|---|
| `ibex diff OLD.y NEW.y` | 記号・規則・競合・状態数・警告の差分。追加／削除／変更の 3 分類。`--format=json` | CI で PR に文法変更の影響を出せる |
| `ibex metrics grammar.y` | 規則数・代替数・平均分岐度・最大再帰深さ・ε 規則数・競合数・状態数 | スキーマを `schema/` に置く |
| `ibex reduce` | 失敗入力／文法の最小化（delta debugging）。競合の最小再現部分文法も出す | ファジング失敗が自動最小化される |

### 5.7 T0-7 / T0-8: i18n とギャラリー（ライセンス方針を含む）

#### T0-7: 診断の i18n

- 全診断メッセージをカタログ化（`lib/ibex/messages/{en,ja}.yml`）。`--lang` / `IBEX_LANG`。
- **既存の `E00xx` エラー ID 空間とは別空間**にする（`E00xx` はユーザのメッセージカタログのキーであり［確］、混ぜてはいけない）。

- カタログ網羅性 CI（コード中のメッセージ ID が全言語に存在する）。

#### T0-8: ギャラリーとライセンス方針（**第 1 版の抜け**）

第 1 版はギャラリーに `c-subset.y` / `python-indent.y` / `js-asi.y` / `ruby-subset.y` を置くとしたが、**これらを既存の第三者文法から持ってくるとライセンス汚染が発生する**。MIT ライセンスのリポジトリに GPL の文法や、別ライセンスの文法を同梱すると配布条件が破れる。

**方針（既存のクリーンルーム／自作方針［確］と整合させる）**

> **G1. ギャラリーに置く文法はすべて自作とする。** 既存のベンチマークが「自作の代表文法」を使う方針［確］と同じ。
> **G2. 第三者の文法は同梱しない。** 検証に使う場合は CI で取得し、成果物には含めない。取得先とライセンスを `gallery/EXTERNAL.md` に記録する。
> **G3. 各ギャラリー文法に `LICENSE`（リポジトリと同じ MIT）と「言語仕様を参照したが実装は自作である」旨の由来記述を置く。**

#### 6.1.1 T1-L1: DFA バックエンド

**動機**: 現在の生成レキサは各状態の規則を現在位置で試し、最長一致・宣言順タイブレークで決める［確］。ReDoS はヒューリスティック lint 止まり［確］。DFA 化すると (a) 規則数に依存しない走査、(b) ReDoS の構造的排除、(c) インクリメンタル字句の再開点定義、が同時に得られる。

**設計**

1. **対応する正規表現の部分集合を先に確定する（ADR）**: 文字・エスケープ・文字クラス（範囲・`&&`・否定・POSIX ブラケット・`\p{...}`）・`.`・`|`・貪欲量指定子 `* + ? {m,n}`・グループ・アンカー `\A \z \Z ^ $`・`\b`・オプション `i m x`。
   **非対応**: 後方参照、先読み／後読み、原子グループ、possessive、再帰、条件、`\G`。
   非対応構文は **`lexer_dfa_unsupported` として位置付きエラー**にする。黙って regex 経路に落ちてはいけない（性能特性が静かに変わるのが最悪）。
2. **文字等価クラス**: ソート済み半開区間の配列＋二分探索。`\p{...}` は**同梱した Unicode データから区間を計算する**（版を固定するため。T1-L9）。
3. **NFA → DFA → Hopcroft 最小化**: 受理状態は「どの規則の受理か（優先度付き）」でラベル分割する。予算（状態数上限）と超過時の明示的失敗を持つ。
4. **最長一致**: 最後の受理位置を保持し、行き止まりで 1 回だけ巻き戻す。
5. **等価性検証（本項目の安全性の核）**: `ibex lex --compare-engines` で、同一 Lexer IR に対する regex エンジンと DFA エンジンのトークン列完全一致を、全ギャラリー × コーパス × 生成入力で検査する。CI 必須。

**既定の切替**: 当面 `regex` を既定に保つ。DFA は opt-in → 2 リリースの field 期間 → **既定切替は別 ADR で判断**する。切替後も `--lexer-engine=regex` は残す。

#### 6.1.2 T1-L4: インデント感応字句

- 行頭空白幅からインデントスタックを更新し `INDENT`/`DEDENT`/`NEWLINE` を発行する。開き括弧内では抑制する（暗黙行継続）。
- **CST では幅 0 トークンとして出す。** これによりインデント言語でもロスレス往復とフォーマッタが成立する。
- 不整合なインデントは `indent_mismatch` 診断。緩い言語向けに最寄りへ丸めるオプション。
- 論点: 幅 0 トークンが既存の trivia 所有ポリシー 3 方式［確］と干渉しないか。特に `--cst-trivia=drop` は座標 API を無効化する［確］ため、インデント言語との組み合わせを禁止する必要があるかを ADR で決める。

#### 6.1.3 T1-L5/L6: トークン列フィルタ（**第 1 版の過大主張を訂正**）

**第 1 版の誤り**: 「純粋なトークン列フィルタで JavaScript の ASI を実現できる」と書き、`gallery/js-asi.y` を DoD にしていた。これは**不可能**である。

理由: JavaScript の自動セミコロン挿入の中心規則は「**攻撃的トークンが構文的に許容されないとき**に、その前に改行があればセミコロンを挿入する」であり、**解析可能性の判定を要求する**。有限窓とカウンタしか持たない純粋フィルタでは表現できない。

**訂正後の設計: 2 つの機構に分ける**

**(A) T1-L5 純粋トークンフィルタ**（機械的に決まる書き換えのみ）

```
filter
  # 制限付き生成規則: return/throw/break/continue の直後の改行
  rule restricted: NEWLINE when prev in [RETURN, THROW, BREAK, CONTINUE] => emit SEMI
  # 閉じ括弧・EOF の直前の改行
  rule before_close: NEWLINE when next in ['}', $eof] => emit SEMI
  rule other_newline: NEWLINE => drop
  # C++ の >> をテンプレート閉じに分割する（括弧深さのみを見る）
  rule shr: SHR when angle_depth > 0 => emit '>', '>'
end
```

- 状態は**有限窓（既定 1、`window: k`）と宣言された整数カウンタのみ**。任意コードは書けない。
- 操作は `emit` / `drop` / `replace` / `insert` の 4 つ。宣言順に最初に一致したものだけが発火。
- 逆写像を保持し、挿入トークンは幅 0 の合成トークンとして CST に現れる。
- **非停止の静的検査**: `insert` 後は必ず入力を 1 つ以上消費する規則しか書けない。
- **無宣言ならこの段は生成されない**（ゼロコスト）。

**(B) T1-L6 エラー駆動トークン挿入**（解析可能性に依存する書き換え）

既存の `RepairPolicy` は「有界コストの挿入・削除・置換を非実行探索で行い、選択したプランを 1 回報告してから通常再生する」［確］。ASI の本質はこれと同じ形なので、**新しい機構を作らず既存機構の宣言的な特殊化**として提供する。

```
%recover insert: SEMI when: newline_before cost: 0 report: none
```

- 意味: 構文エラー時、直前に改行があれば `SEMI` の挿入をコスト 0 で試す。成功したらエラーとして報告しない。
- 既存の修復探索・`on_repair` 観測・`:need_more` 契約をそのまま使う。
- **論点**: 「エラーとして報告しない」修復を許すと、真の構文エラーが隠れる危険がある。`report: none` を使える条件（コスト 0 かつ宣言された単一トークンのみ）を ADR で厳格に制限する。

**ギャラリーの DoD 訂正**: `js-asi-subset`（機械的部分のみ、限界を `README.md` に明記）とする。「JavaScript の ASI を完全に実装した」とは主張しない。

#### 6.1.4 T1-L8: ソフトキーワード（**第 1 版の設計誤りを訂正**）

**第 1 版の誤り**: 「現在状態で `MATCH` が受理可能かをテーブル参照 1 回で判定する」と書いた。**誤りである。** LAC による正確な受理可能性判定は縮約と goto をスタック上で模倣する必要があり［確: `expected_tokens_exact` はスタックをコピーして模倣する］、状態だけでは決まらない。状態のみの判定は歴史的な `expected_tokens` に相当する近似であり、これを使うと「受理可能と判定してシフトしたが後で失敗する」ことが起こる。

**訂正後の設計: 3 値の事前計算 + 必要時のみ実行時 LAC**

生成時に、各状態 × 各ソフトキーワードについて次の 3 値を計算する。

| 値 | 条件 | 実行時の動作 |
|---|---|---|
| `always` | その状態に `MATCH` の明示 shift エントリがあり、縮約を経ずに決定できる | 1 ビット参照で `MATCH` としてシフト |
| `never` | どのスタックからも `MATCH` が到達不能（上方近似で判定） | 1 ビット参照で `IDENT` としてシフト |
| `depends` | それ以外 | その場合のみ既存の LAC 模倣を実行して決める |

- `never` の判定は**上方近似**で行う。「到達不能」と言えるのは近似上でも不能なときだけなので、誤って `IDENT` に落とすことがない。
- `depends` は実行時コストがあるが、実測で稀であることを示す（ギャラリー文法で `depends` 状態の割合を計測して記録する）。
- **決定性の検査**: あるスタックで `MATCH` と `IDENT` の両方が受理可能になり得る場合、それは曖昧である。生成時に**上方近似で検査し、可能性があれば `soft_keyword_conflict` エラー**にする（保守的に失敗する側に倒す）。
- CST では 1 トークンのまま。どちらとして扱ったかを `syntax_kind` に記録する。

#### 6.2.1 T1-A1: 局所 LR(k)（**第 1 版の設計誤りを全面訂正**）

**第 1 版の誤り**: 「判別集合は過剰近似してはならない。到達可能語の展開は**下方近似**で作る」と書いた。**これは健全性の議論として逆である。**

**正しい定式化**

競合セル（状態 s、先読み終端 t、競合行動集合 A = {a₁, a₂, …}）について、各行動 aᵢ が「その後の成功する解析で許す、長さ ≤ k の終端列」の集合を L(aᵢ) とする（t を先頭に含む）。実際の入力の先読み語 w に対して、正しい行動は w ∈ L(aᵢ) を満たす aᵢ である。

ここで各 L(aᵢ) の**上方近似** U(aᵢ) ⊇ L(aᵢ) を計算し、次を検査する。

> **分離条件**: 長さ ≤ k の語について U(a₁), U(a₂), … が**対ごとに素**である。

分離条件が成立すれば、w ∈ L(aᵢ) ⊆ U(aᵢ) より **w が属する U はちょうど 1 つ**であり、行動は一意に決まる。これが健全性である。

- **下方近似では健全にならない**: L'(aᵢ) ⊆ L(aᵢ) が対ごとに素であっても、L(aᵢ) 同士が素であることは導けない。第 1 版の記述は誤りだった。
- **上方近似の計算法**: オートマトンから k ステップ分の（reduce → goto → shift）遷移を展開して到達可能な終端列を集める。スタック下部が未知である部分は「その状態に到達し得る任意のスタック」として扱う（＝上方に振れる）。これは既存の反例探索が扱う設定探索と同じ構造だが、**目的が逆（反例は下方＝実在する語、判別は上方＝あり得る語）である**点に注意して実装する。同じ探索器を共有するなら、近似方向をパラメータにする。
- **分離できない場合**: k を 1 増やして上限まで再試行。上限で失敗したらその競合は解決されない（現状と同じ扱い）。

**どの U にも属さない語が来た場合（第 1 版が扱っていなかったケース）**

k 語の先読みが U のどれにも属さない場合、その入力は解析不能である。しかしここで即座にエラーを出すと、**LR(1) が報告するエラー位置と異なる位置でエラーが出る**。これはメッセージカタログ（文表キー）［確］と `%recover`／修復の挙動を変えてしまう。

そこで次を規約とする。

> **T1-A1 の規約**: 局所 LR(k) は**曖昧性解消の装置であり、エラー検出の装置ではない**。どの U にも属さない語が来た場合、局所 LR(k) は「LR(1)／優先順位が選んだであろう既定行動」を選び、以降の通常のエラー検出機構に委ねる。これによりエラー位置とエラー ID の意味が LR(1) と同一に保たれる。

**その他の制約**

- 先読み語のバッファリング中に**アクションを実行しない**（既存の非実行原則）。push パーサでは `:need_more` を返す（既存の修復と同じ契約［確］）。
- 競合のない状態は表も実行経路も変わらない。判別 DFA は競合セルにのみ紐づく（＝ゼロコストが構造的に保証される）。
- `verify` に **V9（判別 DFA の健全性）**を追加する: 各競合セルについて、記録された U が上方近似であること（サンプリングで反証を探す）と、分離条件が成立していることを独立に検査する。
- **メッセージカタログ影響**: 競合セルの解決が変わると到達可能なエラー状態が変わる。`ibex errors --update` の実行が必要になることを生成時に警告する（§7.1）。

**着手前に解くべき論点**

1. 上方近似の計算量。k=3 で実用的な時間に収まるかをスパイクで測る。
2. 上方近似が緩すぎて分離条件がほとんど成立しないなら、この機能に価値はない。**代表 5 競合で分離が成立するかをスパイクで確認してから実装に入る。**
3. 既存の反例探索器を近似方向パラメータ付きで共有できるか、別実装が必要か。

#### 6.2.3 T1-A3: 状態最小化（**第 1 版の抜けを補う**）

第 1 版は「行動が同一な状態を統合する」としか書かず、等価関係を定義していなかった。これは**既定縮約の互換契約を壊す**危険がある。

既存の契約: 既定縮約は「明示的なエラーマスクが全終端の参照結果を保持し、符号化される ACTION エントリ総数を減らす場合にのみ選択される」［確］。つまり**エラーセルは意味を持つ情報**である。

> **T1-A3 の等価関係**: 状態 p と q を統合してよいのは、次のすべてが一致する場合のみ。
> 1. 既定行動を展開し**エラーマスクを適用した後**の ACTION 行（＝エラーセルの位置も一致すること）
> 2. GOTO 行
> 3. 既定行動そのもの
> 4. 紐づく resolver（優先順位解決・判別 DFA・ガード）
> 5. `%on_error_reduce` による充填結果
> 6. 同期トークンに対する挙動

エラーセルを等価関係に含めないと、**エラー検出のタイミングが変わる**。これは互換性の破壊であり、`--warnings` や `errors` カタログの意味を変える。

**その他の必須事項**

- `merged_from[]` を Automaton IR に記録する。`explain` / `why` / `debug` が最小化後も元の状態を説明できるようにするため。
- **coverage の互換性**: `Coverage::Report` のマージは同一の文法ダイジェスト・表フォーマット・総数を要求する［確］。状態数が変わるのでマージ識別子に**最小化フラグを含める必要がある**。含めないと、最小化した／しないの計測結果が誤ってマージされる。
- `verify` V5（双模倣）合格を必須とする。V5 が未実装の間は最小化を実装してはいけない。
- メッセージカタログの `# state:` ヒントが変わる（文表キー自体は安定なので致命的ではない）。`moved` 分類で検出できることを確認する。

#### 6.2.4 T1-A4: 単位規則除去（**第 1 版の抜けを補う**）

`A: B` 形の規則を除去して表を縮める最適化。第 1 版は「`equiv --map` で木同値を検査」としか書いていなかったが、**より根本的な制約がある**。

> **T1-A4 の制約**: `pragma cst` と併用できない。CST は「すべてのシフトと縮約に対して具体構文ノードを作る」［確］ため、除去された非終端のノードが木から消える。これは CST の契約違反である。生成時にエラーにする。

また意味アクションと位置の保存が必要なので、既存の `%inline` 合成アクション計画の仕組み［確］を再利用する（新しい仕組みを作らない）。`type` 宣言された記号や `%printer` を持つ記号は除去対象から外す（宣言された記号が消えると宣言が無意味になる）。

#### 6.3.1 T1-M2: 規則の拡張・上書き（**不変性契約との整合を補う**）

既存の契約: `Resolution` は「所有する AST と防御的な由来コピーを再帰的に凍結し、include チェーン参照のために規則の同一性を保持する」［確］。

第 1 版は `%override` を「対象定義の全代替を置換する」と書いたが、**凍結された AST を書き換えることはできない**。

> **T1-M2 の実装制約**: `%extend`/`%override`/`%remove` は**解決済み AST を変更しない**。Resolver は「元の解決結果」と「合成指令のリスト」の両方を保持し、Normalizer が**新しい正規化結果を構築する**（元を破壊しない）。規則の同一性は元の AST 側に残り、合成後の生成規則は `composition_origin` で元を指す。

意味論（第 1 版から維持、8 項目）:

1. `%module NAME` はルート／フラグメント先頭で 1 回。省略時は無名（現状互換）。
2. `import ... as X` で名前空間。`as` なしは現状どおり平坦マージ。
3. `hide` は可視性のみ。到達可能なら記号は残る。
4. `rename A => B` は import 側の名前のみ変更。IR は `origin_name` を保持。
5. `%extend` は代替を末尾に追加（宣言順で決定的）。
6. `%override` は対象不存在なら位置付きエラー（タイポで新規定義にならない）。
7. `%remove` 後に参照が残れば通常の未定義非終端エラー。
8. 同一対象への複数操作はエラー（暗黙の優先順位を作らない）。

**安全装置**: `composition_conflict` 診断（合成前には無く合成後に現れた競合を、原因宣言位置付きで報告）。既存の複合競合判定（単独構築との競合指紋比較）［確］を再利用できるかを最初に確認する。

#### 6.3.2 T1-M5: `%feature` / `%if`

**層の明確化（第 1 版が曖昧だった点）**

| 層 | `%if` の扱い |
|---|---|
| Frontend / SourceDocument | **AST ノードとして保持する。** 文字列レベルのプリプロセッサではない |
| Formatter | 通常のトークンとして扱う。無効な代替のバイト列も保存される |
| CST | 条件ブロックを保持する |
| **Normalizer** | **ここで初めて条件を評価し、無効な代替を落とす** |
| Builder 以降 | 現状と完全に同じ入力を見る（＝ゼロコスト） |

フラグ集合は生成時に完全確定する（実行時分岐なし）。式は `and`/`or`/`not`/括弧のみ。`ibex matrix` で組み合わせごとの競合数を出す（既定は全 on / 全 off / 各 1 flip の線形集合）。

#### 6.4.1 T1-S1: 継承属性（**第 1 版の過大評価を訂正**）

**第 1 版の誤り**: 継承属性を「新機能」として提案し、`%inherit` を導入するとした。しかし敵対的検証の結論は次のとおり。

1. **LR では原理的に、縮約前に「どの生成規則の中にいるか」が確定しない**ため、一般の継承属性は素直に定義できない。
2. ibex には既に**中間アクション**があり、これは空のヘルパ生成規則に低下される［確］。その縮約が起きた時点で「その位置までは確定した」ことになるので、**中間アクションで値を設定し、後続の RHS 位置から `_values` や名前付き参照で読む**という形で、実用上の継承属性はすでに書ける。
3. したがって新機能の実質的な差分は次の 3 点だけである。
   - 型付きの宣言（RBS 生成）
   - **エラー回復・修復・（将来の）GLR 分岐でスタックが正しく巻き戻ること**
   - 低下された EBNF ヘルパ（`stmt*` など）の内側からも見えること

**訂正後の位置づけ**: 「継承属性の新規導入」ではなく「**中間アクションで表現されている慣行に、管理されたスタックと型を与える糖衣**」として提案する。Experimental 据え置き。

**着手前に解くべき論点**

- 中間アクションは空ヘルパ生成規則を作るため**競合を増やす**ことが知られている。既存の `midrule_origins`［確］で追跡できるが、`%inherit` が暗黙に中間アクションを挿入すると、ユーザには見えない競合が生まれる。**暗黙挿入を許すかを ADR で決める**（推奨: 許さない。明示的な中間アクションを要求する）。
- 低下された EBNF ヘルパの内側への可視化は、動的スコープ（属性スタックの深さで解決）になる。回復時の巻き戻しと GLR 分岐時のコピーの意味を定義する必要がある。
- **宣言がなければ属性スタックを確保しない**（既存の位置スタック遅延確保［確］と同じ方針）。

#### 6.4.2 T1-S2: `%destructor`

**Ruby では GC があるため価値が薄い。** 実際に必要になるのは次の 2 つの場合に限る。

1. **C ターゲット**（§6.6）でのメモリ解放
2. 意味値が外部リソース（ファイルハンドル等）を保持しており、回復・修復・GLR 分岐破棄で捨てられる場合

したがって **C ターゲットに従属させ、単独では実装しない**。実装する場合は、yacc 回復・panic 同期・有界修復・GLR 分岐破棄の**全経路**で呼ばれることを試験する（漏れがあると意味がない）。

#### 6.5.1 T1-E1: インクリメンタル Stable 化

既存の実測は「Stage A に対して 1.04〜2.83x、fresh syntax session に対して 1.66〜4.48x」［確］。**第 1 版は「p95 < 5ms（10k 行）」という絶対値目標を置いたが、これは既存実測と無関係な数値であり撤回する。**

**正しい要件**

1. **正しさが Stable 化の唯一の根拠**: ランダム編集列に対し「編集後の木 == 同じ最終テキストを新規解析した木」を性質試験で検査する（既存の固定シード試験を性質試験に拡張する）。
2. **再利用条件を仕様化する（ADR）**: 「同一 LR 状態 かつ 同一先読み種 かつ 内部にエラーノードを含まない かつ 編集範囲と交差しない」。判定は常に保守的側（再利用しない）に倒せば安全。
3. **性能契約は相対値で書く**: 「fresh session に対する改善率が既存実測を下回らないこと」。絶対 ms は環境依存なので契約にしない。
4. ファイル先頭の編集は最悪ケースで全再解析になる。これを**契約上の既知の限界として文書化する**（隠さない）。
5. セッション状態はセッション所有（テーブルに置かない）。既存の Ractor 共有可能テーブル契約［確］を壊さない。

#### 6.6.1 多言語対応の適用範囲（**第 1 版が埋めていた caveat を前面に出す**）

意味アクションは Ruby コードである。したがって:

> **多言語ターゲットが成立するのは、アクションを持たない（`@node` のみの）文法に限る。** アクション付き文法から他言語のパーサは作れない。`action_language` がターゲットと一致しない場合は**生成前エラー**とする。

これは弱点ではなく**設計上の誘導**である: 多言語対応したい文法は `@node` 中心に書く、という規範が自然に生まれる。ただし対外的には次のように正確に述べる必要がある。

- ✅ 「アクションを持たない文法から、複数言語の**同一挙動**のパーサを生成できる（適合試験で検証済み）」
- ❌ 「どんな文法からでも複数言語のパーサが出る」

**適合試験の 4 項目**: 受理／拒否、AST の正規化表現（S 式）、エラー ID と位置、リソース制限超過時の挙動。**合格するまでそのターゲットを Preview に上げない。**

#### 6.7.1 T1-G1: ハイブリッド GLR の再挑戦条件

既存の記録: 「GLR と `%dprec`/`%merge` は製品に入らなかった。遅延アクションのスパイクが ≤5% 決定的オーバーヘッドと曖昧性ポリシーのゲートを満たさなかった」［確］。**この判定は正しい。遅延アクション方式では通らない。**

第 2 版が提案する方式と、それに対応するゲート:

| # | 条件 | なぜこれで元のゲートの意図を満たすか |
|---|---|---|
| G1 | **競合が 0 の文法では、`--parser=glr` を指定しても GLR ランタイムを require しない** | 競合の有無は生成時に判明する。決定的利用者への負担が構造的に 0 になる（測定ではなく構造で保証） |

| G3 | **曖昧性ポリシーの宣言が必須**（`%ambiguity error` 既定 / `first` / `merge` / `forest`）。無宣言で曖昧を許さない | 元のゲートの「曖昧性ポリシー」要件を満たす |
| G4 | **アクションの純粋性要件を明文化する**: 分岐中に実行が保留されるため、副作用を持つアクションは `%ambiguity error` 以外では未定義とする | 分岐で副作用が複数回／順序不定に実行される事故を防ぐ |

**スパイクで測ること**: G1/G2 が実装で本当に成立するか（生成器が 2 種類のパーサを出し分けられるか）、GLR 版の `verify` に相当する検証が定義できるか。**4 条件が揃わなければ再度不採用にし、その記録を `stability.md` の Research decisions に追記する。**

## 7. 横断的制約（すべての機能が守ること）

第 1 版はこの節を持っていなかった。個別機能の設計だけを書くと、**機能間の干渉**が漏れる。

### 7.1 表を変える機能が必ず評価すること

局所 LR(k)・状態最小化・単位規則除去・Pager・GLR・`%extend` は、いずれも**表の形か状態の集合を変える**。その場合に必ず評価・文書化すること:

| # | 影響 | 必須の対応 |
|---|---|---|
| C1 | **メッセージカタログの無効化** | 文表キーは安定だが、到達可能なエラー状態が変わると `moved`/`uncovered` が発生する［確］。生成時に「`ibex errors --update` の実行が必要」と警告し、移行手順をリリースノートに書く |
| C2 | **エラー検出タイミングの変更** | 検出位置が LR(1) と異なるなら、それは互換性の変更である。既定で発生させてはならない。§6.2.1 の規約のように「エラー検出は変えない」設計にする |
| C3 | **`ibex coverage` の互換性** | 状態数が変わるとマージ識別子が変わる［確: マージは同一ダイジェスト・表フォーマット・総数を要求］。識別子に当該機能のフラグを含める |
| C4 | **CST との併用可否** | CST は全シフト・全縮約にノードを作る［確］。生成規則や状態を消す最適化は CST と併用できない場合がある。可否を明示し、不可なら生成時エラー |
| C5 | **`explain` / `debug` / `why` の説明可能性** | 状態を統合・生成規則を除去したら、元を指す情報（`merged_from` 等）を必ず IR に残す |
| C6 | **`%expect` / `%expect-rr` の意味** | 競合数が変われば宣言値が合わなくなる。移行手順を書く |
| C7 | **表フォーマット版** | 新フィールドが必要なら v7 の設計に含める（§4.3 の ③） |

### 7.2 ランタイムに状態を追加する機能が守ること

DFA 字句・トークンフィルタ・インクリメンタルセッション・継承属性・GLR は可変状態を持つ。

| # | 制約 |
|---|---|
| D1 | 可変状態は**セッション所有**とし、テーブルに置かない。テーブルは凍結・Ractor 共有可能を維持する［確］ |
| D2 | すべての可変状態に `ResourceLimits` の予算を与える。超過は `ResourceLimitError`［確］ |
| D3 | 状態を持つ機能を使わないパーサでは、その状態を**確保しない**（既存の位置スタック遅延確保と同じ方針［確］） |
| D4 | 単一インスタンスは重複した駆動を拒否する既存契約［確］を維持する |
| D5 | 観測イベント［確］に新しい種別を足す場合は加算的に行い、既存の順序契約を変えない |

### 7.3 診断を追加する機能が守ること

| # | 制約 |
|---|---|
| E1 | 警告種別名は加算的に増やす。スキーマ v1 リーダは未知種別を無視できる［確］ |
| E2 | 位置情報を必ず持つ |

## 8. 文法構文の追加規則

現行ポリシーでも、**§2.2 B3 により新規文法構文を含む開発トラックは同時に 1 個まで**とする。以下の規則はリリース番号に関係なく適用する。

1. **すべての新宣言は `%` 接頭辞を持つ。** 裸の宣言を新設しない（racc 互換文法中の非終端名と衝突する危険がある）。
2. **アクション本体（`{ ... }`）は常に不透明。** 既存のアクションスキャナの契約［確］を変えない。
3. **`@` 接頭辞は代替に付ける注釈専用**（`@node` 既存、`@fmt` / `@highlight` / `@list` / `@skip`）。アクション内の `@1` / `@$` とは名前空間が異なる。
4. **すべての新構文は extended モード限定**。default モードでは構文エラーにする（黙って無視しない）。
5. **frontend の `grammar.y` を変更し、再生成物をコミットする**［確: 自己ホスト］。`shadow_grammar.y` の対応も検討する。
6. **予約語を増やさない。** `%module` を追加しても `module` という非終端名は書ける。
7. **宣言位置を IR に保持する**（診断・フォーマッタ・ロスレス CST のため）。

### 8.1 T1 で導入を検討する宣言（重複整理済み）

第 1 版は 39 の宣言を並べたが、重複と些末なものを除いて 21 に整理した。

## 9. IR 進化計画

### 9.1 T0 で確立した基準

**T0 は IR を変更しない。** T0 はすべて既存 IR を読むだけのツールとして実装し、公開済み IR の契約を維持する。

### 9.2 schema 進化が必要になった場合の順序（§4.3 の再掲）

```
① Automaton IR v3 の封筒（フィールド追加 0 の PR）
② Grammar IR v3 の封筒（フィールド追加 0 の PR）
③ テーブルフォーマット v7 を「一度に」設計する ADR
④ 個別機能のフィールドを ADR ごとに加算
```

**凍結ポリシーの遵守**［確: 既存 closed schema は未知フィールドを拒否し、実験的データは新しい加算的スキーマ版から始めなければならない］:

| 経路 | 使う場面 | 手続き |
|---|---|---|
| A: 既存版へのオプショナル加算 | 意味を変えず、旧リーダが無視しても正しく動く情報 | マイナーリリース。旧文書のバイト安定往復を維持 |
| B: 新メジャースキーマ版 | 意味の変更・必須フィールド追加・実験的封筒 | 新版番号。`Migration.to_version` に冪等な上げ道を追加。直前メジャー版の読み込みを継続 |

**判断が微妙なときは常に B。**

### 9.3 新 IR を増やす条件

第 1 版は TokenFilter IR / Semantics IR / Target IR の 3 つを新設していた。第 2 版では次を条件にする。

> **独立した新 IR を切るのは、(a) 独立にバージョンを刻む必要があり、(b) 単独で消費される用途があり、(c) 既存 IR への埋め込みでは表現が破綻する場合のみ。** 既存の Lexer IR v1 が Grammar IR v2 に埋め込まれつつ独立版を持つ形［確］が模範であり、まずこの形を検討する。

この基準に照らすと、TokenFilter は Lexer IR の次版に埋め込むのが妥当。Semantics IR は `@fmt` が実際に必要になってから判断。Target IR は多言語ターゲットに着手する時点で判断。

## 10. 安全枠組み

### 10.1 6 つの不変条件

| ID | 不変条件 | 検査 |
|---|---|---|
| **I1** | 互換モード（`--mode=default`・pragma なし）の観測可能な挙動は変わらない | racc 互換黒箱試験 + 生成物 golden |
| **I2** | 新データは既存 closed schema に混入しない | IR バリデータの未知フィールド拒否試験 + migration 冪等性 |
| **I3** | **PR の前後で**、当該機能を使わない文法の生成物はバイト同一。意図的変更は golden 更新としてレビューされる | `rake test:zero_cost` + `rake golden:update` の差分 |
| **I4** | 生成物は決定的・バイト安定・トランザクショナル | 2 回生成のバイト比較、`--manifest` 検証、失敗注入 |
| **I5** | 解析経路はユーザコードを実行しない | 「実行されたら失敗するアクション」を含む文法を全解析コマンドに通す |
| **I6** | **（追加）予算のない探索・入力依存の Ruby 再帰が存在しない** | 深いネスト入力（10⁵）と巨大入力での停止性試験 |

I3 の定式化は第 1 版から訂正済み（§5.1）。I6 は第 1 版で HR として書いていたものを不変条件に昇格した（既存コードが徹底している作法［確: 明示的ワークリスト、境界付き探索］に合わせる）。

### 10.2 昇格ゲート

| 領域 | Experimental 入り | Preview 昇格 | Stable 昇格 |
|---|---|---|---|
| ツール（T0） | 欠陥注入で検出能力を実証 | 全ギャラリーで動作 + 誤検出率の計測 | 2 リリース仕様変更なし + 文書完備 |
| アルゴリズム | 代表 5 文法で `verify` 合格 + 状態数実測 | 全ギャラリーで `verify` 合格 + §7.1 の C1〜C7 評価完了 | 2 リリース + 適合試験 |
| 字句 | regex エンジンとトークン列一致 | 全ギャラリー一致 + 性能実測 | 2 リリース + 既定切替の別 ADR |
| 文法構文 | frontend で解析可 + フォーマッタ往復可 | ギャラリーで実使用 + 診断完備 | 2 リリース + shadow grammar 対応 |
| ランタイム | §7.2 の D1〜D5 遵守 | 観測整合 + 適合試験 | 2 リリース + 全ターゲット実装 |

### 10.3 機能フラグの 3 層と矛盾時の規則

| 層 | 手段 |
|---|---|
| 文法内 | `pragma` / `%feature` / `%grammar_class` |
| CLI | `--mode` / `--algorithm` / `--target` / `--feature` |
| ランタイム | ポリシーオブジェクト（`RepairPolicy` / `ResourceLimits` / 新規 `AmbiguityPolicy`） |

**矛盾時はエラー**。「CLI が勝つ」も「文法が勝つ」も選ばない。ただし `--feature` が文法の `default:` を上書きするのは矛盾ではない（それが目的）。

### 10.4 ロールバック可能性

- 1 PR = 1 不変条件 = 1 リバート単位
- T0 は新規ディレクトリの削除で戻せる
- IR の版上げは「読み込み継続」があるので生成側だけリバートできる
- テーブルフォーマットの読み能力は常に前方互換（読みだけ残す）
- Experimental の削除は予告不要［確］。削除時は CHANGELOG に理由と代替を書く

## 12. T2: 却下・保留（11 項目）

| 案 | 判断 | 理由 |
|---|---|---|
| 実行時任意コードの意味述語（ANTLR の `{...}?`） | **却下** | 非実行解析原則と衝突。`%if`（静的）で代替 |
| `%guard`（縮約時ガード） | **保留（第 1 版から降格）** | 純粋性を検査できず、`verify` V8 との整合に追加設計が必要。`%if` で足りる場面が多い。需要が実証されるまで着手しない |
| Packrat / PEG ランタイム内蔵 | **却下** | 決定性と診断品質を捨てる。PEG は取り込みのみ |
| 型検査器生成 | **却下** | 非目標 |
| Earley / GLL | **保留** | GLR が失敗した場合の代替として記録するのみ。LR 資産（表・反例・検証器）を再利用できない |
| 独自正規表現エンジンの全面採用 | **却下** | Ruby `Regexp` 意味との乖離が利用者に見える |
| 文字列レベルの `#ifdef` | **却下** | ロスレス CST とフォーマッタが壊れる |
| 並列字句 / 投機的分割解析 / ストリーミング / 巨大ファイル対策 | **保留（第 1 版から降格）** | §1.2 の「戦わない領域」。moat への寄与が小さい |
| 遅延アクション方式の GLR | **却下（既存記録の追認）** | ≤5% ゲートを構造的に満たせない［確］。ハイブリッド方式（§6.7）のみ再挑戦の余地 |
| ANTLR4 / tree-sitter / PEG の取り込み | **保留** | bison 取り込み（T0-9）の実績を見てから判断。取り込み先の文法ライセンスにも注意（§5.7） |
| 文法パッケージ配布（レジストリ） | **保留** | 配布物の互換性、署名、ライセンス、撤回ポリシーを支える需要と運用体制が未実証 |
