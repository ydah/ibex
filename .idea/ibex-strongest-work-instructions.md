## 1. 絶対規則（Hard Rules）

違反した PR は内容の良否に関係なくマージしない。

| # | 規則 | 検査 |
|---|---|---|
| HR1 | **1 PR = 1 関心事**。機能追加とリファクタと整形を混ぜない | レビュー |
| HR2 | **互換モードの観測可能な挙動を変えない**（`--mode=default` かつ pragma なし） | `rake test:compat` + golden |
| HR3 | **ゼロコスト**: 機能を追加する PR は、その**PR の前後で**当該機能を使わない代表文法の生成物がバイト同一であること。バイトが変わる PR は `rake golden:update` で更新し、**差分そのものをレビュー対象にする** | `rake test:zero_cost` |
| HR4 | **既存の closed schema にフィールドを足さない**。新データは新スキーマ版へ | `rake test:ir_schema` |
| HR5 | **解析経路でユーザコードを実行しない** | `rake test:no_exec` |
| HR6 | **仕様変更には ADR を先に書く**。実装 PR は ADR 番号を参照する | レビュー |
| HR7 | **新 CLI オプション・新宣言はドキュメントに同時に書く** | `rake test:docs_coverage` |
| HR8 | **自己ホスト frontend を変更したら再生成物をコミットする**。再生成物の差分は必ずレビューする（意図しない差分＝バグ） | `rake frontend:generate` + `git diff --exit-code` |
| HR9 | **クリーンルーム境界を越えない**。racc / bison / ANTLR の**実装ソース**を読んで書かない。公開仕様・公開マニュアル・黒箱挙動・**文法ファイル**のみ | PR チェックボックス + レビュー |
| HR10 | **境界のない探索を書かない**。すべての探索・展開・再帰に明示的な予算と超過時の明示的失敗を持たせる | 予算超過試験 |
| HR11 | **入力依存の再帰を Ruby の呼び出しスタックに載せない**。明示的ワークリストを使う（既存 Normalizer の作法） | 深いネスト入力（10⁵）の試験 |
| HR12 | **決定性を壊さない**。Hash 反復順・浮動小数・時刻・乱数・ロケール・TZ に依存した出力を作らない | 2 回生成のバイト比較 |
| HR13 | **feature 予算を超えない。** 新規 Preview 開発トラックは同時 3、うち新規文法構文を含むものは同時 1、Experimental は同時 5 まで（設計書 §2.2 の B2〜B4） | `docs/stability.md` + レビュー |

### 1.1 HR3 の運用手順（第 1 版の訂正点なので詳述する）

```bash
# 1. 機能追加 PR を作る前に、基準を記録する
rake golden:record            # 代表文法の生成物ダイジェストを test/golden/digests.yml に固定

# 2. 実装する

# 3. 検査する
rake test:zero_cost
#    → 緑なら OK（機能 off の生成物が変わっていない）
#    → 赤なら 2 択:
#       (a) 意図しない副作用 → 実装を直す
#       (b) 意図的な変更（生成器のリファクタ等） → 次へ

# 4. 意図的な変更の場合のみ
rake golden:update            # digests.yml と、差分の要約を更新
git add test/golden/          # 差分が PR に現れる
#    PR 本文に「なぜバイトが変わるのか」「利用者に影響があるか」を書く
```

**HR3 の目的は「バイトが不変であること」ではなく「変化が意図的でレビューされること」**である。ここを取り違えると、正当なリファクタができなくなる。

## 2. 作業の型

```
W00 前提検証   → 設計書 §0.2 の確認を実施し、前提のずれを記録する（最初に 1 回）
S0  調査       → 既存実装の該当箇所と影響範囲を文書化する（コード変更なし）
S1  ADR        → 契約を先に書く。受入条件・不変条件・却下した代替案を含める
S2  スパイク   → 使い捨て実装でゲートを測る。マージしない。結果を ADR に追記
S3  実装       → 本実装。テスト先行。1 PR = 1 不変条件
S4  昇格       → stability.md の基準で判定し ADR に記録
```

### 2.0 W00: 前提検証（最初にやる唯一のタスク）

- 規模: S（1 日）/ 依存: なし
- 内容: 設計書 §0.2 のコマンドを実行し、結果を `docs/investigations/W00-assumptions.md` に記録する。
- **必ず確認する 6 点**:
  1. `docs/decisions/` の実際の最大 ADR 番号（設計書は「0081」と仮定しているが根拠が弱い）
  2. 既存の LALR 参照ストラテジと固定シード性質試験の実体（`ibex verify` の位置づけが変わる）
  3. `benchmark/` の現在の基準と非ゲート範囲
  4. ギャラリー相当の既存資産の有無
  5. `schema/` の現況
  6. 生成レキサの現在の実装方式
- DoD: 設計書の前提と食い違った点を列挙し、**食い違いがあれば設計書 §3 を先に修正する PR を出す**。

### 2.3 S2 スパイクの規則

- ブランチ名 `spike/<タスクID>-<slug>`。**マージしない。**
- 目的はゲートを測ることだけ。テストも文書も不要。
- 成果物は ADR に追記する測定結果と判断（Go / No-Go / 設計変更）。
- **No-Go でも記録を残す**（`stability.md` の Research decisions に 1 行）。既存の GLR 不採用の記録が、将来の再挑戦を安全にしている実例。

### 2.4 S3 実装 PR の分割順序

```
PR-1  テストと固定資産のみ（機能未実装、テストは pending）
PR-2  中核実装（1 つの不変条件を満たす最小単位）
PR-3  CLI / 出力形式 / JSON スキーマ
PR-4  診断・警告・i18n カタログ
PR-5  ドキュメント・ギャラリーでの実使用
PR-6  ベンチ・不変条件マトリクスへの登録
```

IR やスキーマを触る場合は PR-2 の前に「封筒だけ（フィールド追加 0）」の PR を挟む。

### 3.6 レシピ F: 新しい CLI サブコマンドを追加する

```
F1. ADR: 入出力、終了コードの意味、JSON スキーマの版
F2. 終了コード規約:
      0 = 成功 / 検出されなかった
      1 = 検出された（競合・曖昧性・差異・違反）
      2 = 予算切れ（探索が完了しなかった）
      それ以外 = 呼び出しエラー（stderr。JSON 封筒を出さない）
F3. --format=text|json。JSON は versioned schema を schema/ に置く
F4. ファイル出力は原子的（同一ディレクトリ rename）。入力のエイリアスを拒否
F5. 解析系はユーザコードを実行しない（HR5）
F6. 予算オプション（--max-*）は正の整数のみ。既定値をドキュメントに書く
F7. **有界検証の結果を「証明」と読める文言で出力しない**
    悪い例: "grammars are equivalent"
    良い例: "no difference found within 30 tokens (this is not a proof of equivalence)"
F8. test/cli/ にテスト（--help の出力も含む）
F9. README.md と docs/ に追記
```

### 3.7 レシピ G: 表または状態集合を変える（**第 2 版で追加**）

対象: 局所 LR(k)、状態最小化、単位規則除去、Pager、GLR、`%extend`、既定縮約の変更。

```

G2. C2（エラー検出タイミング）が「変わる」なら、既定で有効にしてはならない。
    opt-in にし、変わることを文書に明記する
G3. C1（メッセージカタログ）の影響を実測する:
    g3-1. 変更前後で ibex errors --list を実行して差分を取る
    g3-2. moved / uncovered の件数を PR に記載する
    g3-3. 移行手順（ibex errors --update の実行）をリリースノートに書く
G4. C3（coverage）: 状態数が変わるならマージ識別子に当該フラグを含める

    explain / debug / why が変更後も元を説明できることをテストする
G7. ibex verify の該当項目（V4 / V5 / V9 等）に合格する。
    verify に該当項目がなければ**先に verify を拡張する**
G8. ibex equiv で言語同値を確認する
G9. benchmark に状態数・表サイズ・構築時間を記録する
```

**G7 が最重要**。検証項目のない表変換を入れてはならない。

### 3.8 レシピ H: ギャラリー文法を追加する（**第 2 版で追加**）


### 8.2 エージェントに渡すときの注意（第 2 版で強化）

1. **調査（S0）と ADR（S1）で必ず人間のレビューを挟む。** 実装から始めさせると、既存の契約を壊す設計を大量のコードで書いてくる。レビュー地点をテンプレート内に「**ここで止まって**」と明示的に書く。
2. **「やってはいけないこと」を具体的に列挙する。** 特に「効率的に見えるが禁止されている行動」を明示する必要がある。例:
   - 既存ビルダのロジックを検証器にコピーする（効率的に見えるが本タスクを無意味にする）
   - 既存スキーマにフィールドを足す（自然に見えるが凍結違反）
   - ADR 番号を推測する（`ls` すれば分かるのに推測しがち）
3. **「分からなければ調査に戻る」を明示する。** 推測で設計を埋めるのが最も危険。第 1 版の設計書自体が、この失敗（下方近似／テーブル参照 1 回／等価関係の未定義）をしていた。
4. **DoD を自己申告させる。** 各項目について「どのテストで確認したか」を書かせる。書けない項目は未完了。
5. **スコープ縮小を歓迎する。** 「調査したら既存実装で足りていた」は良い成果である。PR 本文にそれを書く欄を用意しておく。
6. **大きすぎる差分は分割を要求する。** 1 PR = 1 不変条件。
7. **既存コードの作法を真似させる。** 明示的ワークリスト、凍結オブジェクト、位置情報の保持、予算付き探索、位置付きエラー。既存コードが徹底しているこれらの作法に合わせるのが最も品質が上がる。

### 8.3 エージェントの出力をレビューするときのチェック

| # | 見るところ | 危険信号 |
|---|---|---|
| 1 | 調査文書に「既存の類似機能」の節があるか | ない → 車輪の再発明の可能性 |
| 2 | ADR に §7 の横断的制約の評価があるか | 空欄 → 干渉の見落とし |
| 3 | 探索・再帰に予算があるか | `while true` / 素朴な再帰 → HR10/HR11 違反 |
| 4 | エラーが位置情報を持つか | メッセージだけ → 既存作法違反 |
| 5 | テストが「実装が通る形」になっていないか | 実装の内部構造に依存したテスト → 仕様から書き直させる |
| 6 | 有界検証の結果を「証明」と書いていないか | "equivalent" → "no difference found within N" に直させる |
| 7 | 生成物のバイトが変わっていないか | `test:zero_cost` 赤で golden 更新もなし → 副作用 |
| 8 | 新機能が同時実行予算を超えていないか | HR13 違反 |
